## Problem Statement

PLAN.md Phase 2 replaces JSON collaboration messages with raw binary Yjs updates.
The client half is written. The server half is not, and the plan's remaining task
list is insufficient to make the feature correct.

The tree is broken end-to-end today. `SessionProvider` sends binary WebSocket
frames, but `CollaborationHandler extends TextWebSocketHandler`, whose
`handleBinaryMessage` closes the session with
`CloseStatus.NOT_ACCEPTABLE.withReason("Binary messages not supported")`. The
failure is *invisible* rather than loud: `CollaborationClient` retries five times
with backoff (lines 87-94), and `SessionProvider` polls `isConnected` only at
250 ms and 1000 ms, so the UI reports "connected" while the socket flaps in a
reconnect loop. All 116 frontend tests pass because nothing exercises the backend.

Underneath that, three design gaps prevent a correct editor even once the socket
stays open: there is no sync handshake for late joiners, the JSON seeding path
duplicates every shape when two clients open the same document, and snapshot-based
undo rewrites peers' canvases the moment binary sync goes live.

## What Makes This Cool

A collaborative canvas where two people drag the same rectangle and it just works
is the "whoa." Getting there on a hand-written Java relay -- rather than importing
a batteries-included backend -- means the CRDT plumbing is legible end to end.
That is the stated point of the project.

## Constraints

- Goal is open source / research: learning value is a first-class requirement,
  which rules out replacing the Java relay with an off-the-shelf backend.
- Existing stack is fixed: React 19 + Vite frontend, Spring Boot 3.4.1 + H2 backend.
- `yjs@13.6.31` and `y-protocols@1.0.7` are already dependencies. `y-protocols`
  is currently unused (zero references in `src/`).
- **H2 is in-memory** (`jdbc:h2:mem:` in `application.yml`). Schema migration is
  free -- there is no existing data -- but nothing survives a JVM restart. Every
  persistence claim below is scoped to one server lifetime until this changes.
- Baby-Steps Protocol is active (PLAN.md): one modifying tool call per turn,
  <=35 lines per edit block, one domain per turn.

## Premises

Settled with the user during this session.

1. **Yjs is the right CRDT engine.** Battle-tested, already a dependency. The
   suite is 116 tests across 14 files; PLAN.md:37 attributes 108 to the Yjs
   engine and PLAN.md:50 attributes 8 to `CollaborationClient`. Accepted as written.
2. **The hand-rolled protocol is NOT sufficient as a wire format.** The outer
   envelope byte (0 = sync, 1 = awareness) that `SessionProvider.tsx:107` already
   writes is correct and matches y-websocket's application layer, which writes the
   same values as varuints. What is missing is the *payload*: `y-protocols/sync`
   messages, including the SyncStep1 / SyncStep2 handshake. Revised: keep the
   envelope, fill it with `y-protocols/sync`.
3. **The backend is NOT a dumb stateless relay.** ARCHITECTURE.md contradicts
   itself: section 2 calls the handler a "stateless broadcast channel," and section
   3 says "On initial join, the full binary document is loaded from the database
   and sent to the client." A stateless relay cannot serve a late joiner when the
   room is otherwise empty. Revised: the room is a stateful participant.
4. **TEXT -> BLOB does not complete the persistence story.** `SessionProvider`
   still seeds each client from `JSON.parse(doc.content)`. Verified empirically:
   two fresh `Y.Doc`s each seeded from `['x','y']` and then merged produce
   `["x","y","x","y"]` -- every shape twice. Deleting that path is a required task,
   and it is absent from PLAN.md.
5. **Phase 3 (Y.UndoManager) is a correctness dependency of Phase 2; Phase 4 is
   not.** The breaking mechanism is `Command.undo()` -> `model.restore(prevStates)`
   (`Command.ts:12-14`), which deletes every tracked item and re-inserts *fresh*
   `Y.Map`s. Replicated to peers, that both deletes shapes they can see and
   introduces duplicate ids. By contrast `broadcastFullState()` is already dead
   code -- `SessionProvider.broadcast` is an empty function body (lines 198-203) --
   so removing `full_state` is cleanup, not a blocker.
6. **The tree is broken right now**, not half-shipped. See Problem Statement.
7. **Rolling your own Java relay beats adopting y-websocket/Hocuspocus** given the
   research goal -- but the WebSocket path must stay protocol-compatible with the
   reference so `y-websocket-server` can be swapped in to bisect bugs. That
   compatibility is load-bearing on the two-leg handshake below. Compaction is an
   out-of-band REST exchange, never a new WS message type.

## Approaches Considered

### Approach A: y-protocols/sync + stateful Java room  [CHOSEN]
Client keeps the envelope byte and puts `y-protocols/sync` messages inside it. The
Java handler becomes a `BinaryWebSocketHandler` whose room owns the document's
truth: it syncs every joiner from its log, and it persists what it receives.
Effort L (human ~2 weeks / CC ~6 hrs). Risk Med.

### Approach B: Handshake-over-REST, dumb relay stays
Same client change, but Spring stays a stateless byte-forwarder; late joiners GET
the persisted blob over REST and clients debounce-PUT `encodeStateAsUpdate()` back.
Effort M (human ~4 days / CC ~1.5 hrs). Risk Med.
Rejected: the server never merges, so persistence is only as fresh as the last
client PUT, and concurrent PUTs overwrite each other's blob.

### Approach C: y-websocket sidecar, Java keeps REST
Delete the relay; run `yjs/y-websocket-server` as a Node sidecar.
Effort S (human ~2 days / CC ~45 min). Risk Low.
Rejected: optimizes away the thing the project exists to learn, and adds a second
runtime to deploy.

## Recommended Approach

Approach A, in two stages. Stage 1 needs no CRDT implementation on the JVM.

**Why Stage 2 is deferred.** Answering SyncStep1 with a *minimal diff* requires
computing a delta from the joiner's state vector, which needs a real Yjs
implementation on the JVM. (Decoding the state vector is varint pairs and is
trivial; the diff computation is the hard part.) The maintained `yrs` bindings are
ywasm, ypy, yrb, yswift, and ydotnet -- **there may be no maintained JVM binding at
all.** Confirming one exists is a prerequisite before Stage 2 is treated as an
evaluable option, not an assumption.

### Stage 1 -- always replay; the handshake has two legs

**The client opens with both legs.** Inside `connect()`'s `ws.onopen` -- not in
`startCollabSession` -- the client sends, in envelope 0:

1. `writeSyncStep1(doc)` -- "here is my state vector."
2. `writeUpdate(Y.encodeStateAsUpdate(doc))` -- "and here is everything I have."

**Both legs must fire on every reconnect, not just the first connect.** That is why
they belong in `onopen`: `CollaborationClient` deliberately does not expose `onopen`
today (lines 71-74, and the comment at `SessionProvider.tsx:112-113` says so), so
wiring them at the `startCollabSession` level would give the self-healing property
on first connect only -- which is exactly the case this design exists to fix.

Leg 2 is what makes the system self-healing. `CollaborationClient.send()` silently
drops frames when `readyState !== OPEN` (lines 111-114), so any edit made while
disconnected exists **only** on that client. Without leg 2, a reconnecting client's
offline work is never recovered and Success Criterion 3 fails by construction. With
it, the server logs the joiner's full state as an ordinary Update(2) and the log
repairs itself after a reconnect.

Cost, stated honestly: leg 2 is logged, and for a client with content it is the
whole document. The log is therefore **O(edits + reconnects x |doc|)**, not
O(edits). Compaction is what keeps that bounded.

**The server always replays.** On join the server sends the joiner:

1. `documents.content` -- the compacted snapshot, if one exists -- as an Update(2);
2. then every `document_updates` row above that snapshot's watermark.

Unconditionally, whether or not other peers are present. Replaying only the log rows
would lose everything below the watermark and fail Success Criterion 5.

Replay is safe to do always: Yjs update application is idempotent and
order-independent (verified against `yjs@13.6.31` -- replaying a log three times and
replaying it in reverse both converge; causally-orphaned updates park in
`store.pendingStructs` until their dependency lands). Making replay unconditional
deletes an entire class of bug: no "is the room empty" branch, no timeout when a
backgrounded tab with throttled timers fails to answer, and no race where a joiner
is answered by a peer that is itself still mid-sync.

**Joining is a locked operation.** Adding the session to the room and snapshotting
what to replay happen under the same room lock. Otherwise an Update(2) arriving
between the two is broadcast to a room the joiner is not yet in *and* sits below the
replay cursor -- lost to that client permanently. This is the same race class the
unconditional replay was meant to remove, and it comes back if the lock is scoped to
`seq` allocation alone.

**No SyncStep1 forwarding.** An earlier draft forwarded a joiner's SyncStep1 to a
peer for a minimal SyncStep2. Dropped: leg 2 plus per-edit Update(2) logging makes
the log a superset of every live peer's state, so a peer's SyncStep2 is a strict
subset of the replay the joiner just received -- duplicate traffic on every join.
(It also has no natural "oldest peer": the room is a `CopyOnWriteArraySet`, which is
unordered.) The one thing it would buy is setting a stock y-websocket client's
`synced` flag. This room is therefore a drop-in replacement for
`y-websocket-server` in one direction only -- **this** client against the stock
server works; a stock client against this room never sees a SyncStep2 and never
marks itself synced. That is acceptable for the bisect use in Premise 7, which runs
in the working direction.

**Message classification.** The handler decodes the envelope byte plus one lib0
varint. Verified constants from `node_modules/y-protocols/sync.js:38-40`:
`messageYjsSyncStep1 = 0`, `messageYjsSyncStep2 = 1`, `messageYjsUpdate = 2`.

| Frame | Broadcast | Log |
|---|---|---|
| envelope 0, SyncStep1 (0) | no -- server answers with replay | no |
| envelope 0, SyncStep2 (1) | to room, excluding sender | no |
| envelope 0, Update (2) | to room, excluding sender | **yes** |
| envelope 1, awareness | to room, excluding sender | no |

Awareness frames are relayed like any other; they simply never enter the document
log. Logging handshake or cursor frames would corrupt replay. **Producing and
consuming awareness frames is Phase 5 and out of scope here** -- Stage 1 only
guarantees the envelope-1 path relays and is never logged.

**Log storage.** Naive concatenation is silently lossy -- verified: `Y.applyUpdate`
accepts two concatenated updates without error and applies only the first.
`Y.mergeUpdates` handles it correctly but is a JS API and unusable from the JVM. So
the log is a `document_updates` child table (`document_id`, `seq`, `payload BLOB`).
`seq` is allocated **per document, by the room object, under the room's own lock** --
not by a JPA identity or a shared DB sequence, both of which produce per-document
gaps by construction. A room is removed from the map when it empties
(`CollaborationHandler.java:71-73`), so a recreated room must seed its counter from
`SELECT COALESCE(MAX(seq),0)` for that document, never from 0, or it collides with
rows that survived an unclean drain. `documents.content` becomes the
compacted-snapshot BLOB.

**Compaction is client-initiated.** The server cannot "ask the last client to
compact" -- by the time the room drains that client is gone, and REST is
client-initiated. So:

- Primary path: the **first client that finishes syncing on a join** POSTs
  `encodeStateAsUpdate()`.
- Best-effort path: a client also POSTs on `beforeunload` / document close.

The server writes the snapshot to `documents.content` with the `seq` watermark it
covers, then deletes log rows `<= watermark` -- append-then-truncate, never replace,
so updates arriving mid-compaction survive.

No size or row thresholds. Given in-memory H2, the log only needs to stay bounded
within one JVM lifetime, and compaction-on-join achieves that. Adding watermark
timers and row budgets buys nothing any success criterion tests. Revisit if and when
H2 moves to disk.

### Stage 2 -- real server-side Y.Doc (optional, gated)

Swap the log for a `yrs`-backed `Y.Doc` per room. Gains server-computed minimal
diffs, server-side GC, and a foundation for document versioning. The client does not
change -- it is already speaking the reference protocol. **Gate:** confirm a
maintained JVM binding exists first. If none does, Stage 2 means writing and
maintaining JNI bindings over `yrs`, which is a different project.

## Open Questions

1. **Log integrity is only a storage check.** The server can verify its log is
   `seq`-contiguous, but that detects DB truncation, not document completeness: an
   update that never reached the server leaves the log gapless *and* short. The only
   true completeness signal is `store.pendingStructs !== null` after replay, a
   client-side observation the server cannot make. Decide whether the client reports
   that back, or whether the two-leg handshake is sufficient mitigation on its own.
2. **Compaction trust.** A *client* produces the compacted state, so a malicious or
   buggy one can compact to a document that drops others' work. Acceptable for an
   OSS research project with no auth; revisit if this gets real users. After a
   compaction, "gapless" means gapless relative to the watermark, not to 1.
3. **`Y.Doc` singleton across documents. Gates every step after step 1.** `model` is
   a module-level singleton (`YjsGraphicModel.ts:356`). `restore()` does **not** mask
   this -- verified: after `restore([])` then `restore(docB)`, the doc still carries
   document A's full op history, and syncing it into a peer legitimately holding
   `["B1"]` yields `["B1","B1"]`. `restore()` only resets the locally visible array.
   The contamination fires the moment binary sync goes live.
   **Prefer a fresh model instance behind a provider over a `model.reset()`.**
   `objects` is `private readonly` and captured in the constructor, `subscribe()`
   closes over `this.doc`, and `useSubscribe` registers in
   `useEffect(..., [updateView])` -- so a `reset()` that swaps `this.doc` orphans
   every mounted subscriber and views stop repainting with no error. The step-3
   `Y.UndoManager` instance has the same lifetime problem. Six production files
   import `@/models/GraphicEditorModel`; 15 files in `src/` reference it.
4. **Transaction origin discipline.** `readSyncMessage(decoder, encoder, doc, origin)`
   needs an origin that `onLocalUpdate`'s `origin !== this` filter
   (`YjsGraphicModel.ts:323`) treats as remote. Today the only such origin is set
   inside `applyRemoteUpdate`, which takes bytes and not a decoder. The model needs a
   new entry point, or the origin sentinel needs to be exported. Undecided.
   Related: `Y.UndoManager` "scoped to local origin" means `trackedOrigins:
   Set([null])`, because every local mutation uses `doc.transact(fn)` with a null
   origin. That is also the default, but state it rather than leave it implied.

Out of scope, tracked separately: `move()` recurses into group children while
`update()` and `remove()` only scan top level. Pre-existing bug, no dependency on
this design; file it as an issue.

## Success Criteria

- Two browsers open the same document, both edit, both converge. No duplicated shapes.
- A third browser joins mid-session and sees the current canvas, including edits
  made before it connected.
- A client disconnected for 30 seconds -- **including one that kept editing while
  disconnected** -- reconnects and converges in both directions. Note this criterion
  is currently untestable by luck: `maxReconnectAttempts = 5` with
  `reconnectDelay * attempts` sums to 2+4+6+8+10 = exactly 30 s, after which
  `shouldReconnect` never fires again and there is no manual retry. Step 2 caps the
  backoff and retries indefinitely so the boundary stops being load-bearing.
- Undo on client A affects only client A's edits and leaves client B's shapes intact.
- All tabs close, then the document is reopened *within the same server lifetime* --
  **including after a compaction has truncated the log** -- and restores the state
  last on screen. (Cross-restart durability needs H2 on disk; out of scope.)
- Swapping the Java handler for stock `y-websocket-server` produces identical
  convergence behavior for this client. This is the bisect lever Premise 7 buys.
- Backend has tests that exercise binary frames. None exist today.

## Next Steps

Ordered. Open Question 3 gates everything after step 1. Undo lands before the
protocol switch, not after: step 4 turns on binary sync, and leaving
`Command.undo() -> model.restore()` live across that boundary arms Premise 5's
failure for a whole step at zero benefit.

**Known gap, steps 3-8.** Step 3 deletes the JSON load and save paths; server-side
replay does not exist until step 7. Documents do not persist across that window.
That is deliberate -- the alternative is maintaining two persistence systems
simultaneously -- but it means the app is not demoable mid-sequence.

1. **Unblock the socket.** `CollaborationHandler extends BinaryWebSocketHandler`,
   implement `handleBinaryMessage`, relay `BinaryMessage`. Wrap each session in
   `ConcurrentWebSocketSessionDecorator(session, 10_000, 4_194_304)` -- Spring
   sessions are not safe for concurrent sends, and drag-rate traffic otherwise
   throws `IllegalStateException: ... [BINARY_PARTIAL_WRITING]`. The decorator
   *closes* the session on buffer overflow, so the limit must exceed a full-document
   frame: measured with this repo's own `objectFactory` rectangle schema,
   `Y.encodeStateAsUpdate` for 200 shapes is **~45 KB**, so every leg-2 frame from a
   moderately full canvas already blows Tomcat's 8192 default
   (`tomcat-embed-websocket` `Constants.DEFAULT_BUFFER_SIZE`) and closes the socket
   with 1009. Raise `maxBinaryMessageBufferSize` to 4 MB via a
   `ServletServerContainerFactoryBean`.
2. **Fix reconnect.** Expose `onopen` on `CollaborationClient` (step 4 needs it),
   cap the backoff, and retry indefinitely instead of giving up after 5 attempts.
3. **Kill the singleton (Open Question 3).** Fresh model instance behind a provider.
   Then delete `loadContentIntoModel`'s `JSON.parse` -> `restore()` and the
   `JSON.stringify(model.snapshot)` save path.
4. **Undo.** Replace `CommandManager` with `Y.UndoManager` (`trackedOrigins:
   Set([null])`), instantiated with the model so its lifetime matches; delete
   `Command.ts`, `CommandManager.ts`, and the snapshot-undo tests.
5. **Client protocol.** Keep the outer envelope byte; replace its payload with
   `y-protocols/sync`. In `ws.onopen` send **both** `writeSyncStep1` and

   `writeUpdate` on local change. Resolve Open Question 4 as part of this.
6. **Persistence schema.** Add the `document_updates` child table;
   `documents.content` becomes `byte[]` / BLOB.
7. **REST ripple.** `DocumentRequest.content`, `DocumentService`,

8. **Room: classification.** Envelope + varint decode, per the table above. One turn.
9. **Room: log + replay.** Per-document `seq` seeded from `MAX(seq)` under the room

10. **Room: compaction (server).** REST endpoint, watermark write, truncate

11. **Compaction (client).** POST `encodeStateAsUpdate()` after finishing a sync,

12. **Cleanup (not a blocker).** Remove the dead `broadcastFullState()` calls, the

13. **Tests.** PLAN.md Phase 6 convergence: two in-process `Y.Doc`s making

  plan's Phase 2 backend list says "On client join: send stored binary state as
  initial sync." The task list was right and the headline was the leftover. Your
